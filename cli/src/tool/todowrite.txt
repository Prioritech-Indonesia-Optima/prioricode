Create and maintain the session todo list — the user's live view of your progress. Any request that modifies files or spans multiple steps requires a todo list, written BEFORE the first change. No list = lost work the moment context is compacted or the process dies; the list is persisted outside the conversation and survives both.

Structure: group work into phases with the optional `phase` label — consecutive tasks sharing a label render as one collapsible group (e.g. "Phase 1: schema", "Phase 2: wiring"). Tasks inside a phase are the concrete steps; finish a phase's tasks before starting the next phase's.

Statuses: `pending`, `in_progress`, `completed`, `cancelled` — anything else is rejected. The tool also rejects a list with more than one `in_progress`, or with work in flight (pending + completed mix) and nothing active.

Discipline (every one is mandatory):
- Write the list before the first edit of any modifying request; one item per logical step/phase.
- Mark `in_progress` the moment you start a task. Exactly one at a time.
- Cross off — mark `completed` — the instant a task is truly done and verified. Never batch completions and never mark completed on intent.
- Update in real time: capture new instructions as todos immediately, append follow-ups you discover, set `cancelled` when scope drops a task.
- Blocked: keep `in_progress`, add a follow-up todo naming the blocker.
- End of turn: do not finish a modifying request with tasks still open unless the user stopped you.
- Preserve user-provided commands verbatim (flags, args, order); items specific and actionable.

Skip only for: a single trivial edit, or purely informational questions. When in doubt, write the list.
