Coordinate with other concurrent PrioriCode sessions working on the same project. Engineers often run several sessions against one codebase; use this tool to discover them, avoid editing files they are actively changing, and exchange coordination notes so your work does not collide.

Actions:
- discover: list sibling sessions in this project with their last-active time, which are busy, the files each has claimed, any UNREAD messages or requests addressed to you, notes already delivered into your context very recently, and a receipt ledger for what you recently SENT. Call this when you need details or must act on a peer; you do NOT need it for basic awareness (see Ambient awareness below). It is the source of valid target session ids.
- claim: declare the file paths this session is actively editing so peers can avoid them. Re-claim as the set changes.
- release: release file-path claims you no longer need.
- send: leave a fire-and-forget coordination note in another session's inbox (target + message). A busy target reads it at its next turn boundary without being interrupted; an idle target is woken within seconds to handle it.
- ask: send a request to another session and wait (up to timeout seconds) for it to respond. The target's standing coordination representative guarantees an answer even if the main agent never reaches a boundary; if the main agent later answers itself, that arrives as a correction. Returns the answer, or — on timeout — exactly how far delivery got (never seen / seen but unanswered / being answered by the responder), and the answer still arrives later.
- wait: re-wait on an existing request you already sent, using its request_id and a fresh timeout. Use this after an `ask` times out instead of re-asking (which would post a duplicate request). Returns the same as `ask`.
- respond: answer a request using its request_id. Only the asked session may respond to requests addressed to it (its standing coordination responder may answer on its behalf when it has not). At most ONE response per request: if your responder already answered, post a correction with `send` referencing the request id instead of responding again.

Delivery and receipts (how to stop guessing):
- Every note moves through a ledger: queued -> seen (injected into the peer's context) -> received (the peer's model step consumed it cleanly). If a delivery dies mid-flight, the note is automatically re-queued and re-delivered — notes are not silently lost.
- After an `ask` timeout, do NOT re-ask in a loop. A late answer is delivered into your context automatically when it lands (and wakes you if you are idle). `discover` shows the receipt status of everything you sent.
- Never send social acknowledgements ("noted", "thanks") back over this channel — silence means noted. Only answer when coordination genuinely needs it.

When a peer answers through its responder:
- Every request is eventually answered: if the main agent has not replied by the time the request ages, a hidden coordination responder child — the session's standing reply representative, quoting a snapshot of that session's recent conversation, todo list, and file claims — answers out-of-band. Such replies are prefixed "[answered by ... coordination responder ...]" and are best-effort: verify anything critical. The main agent is informed of every delegated exchange at its own next turn (a "[handled for you]" note) and may post a corrected answer — you will receive the correction as a follow-up reply.

When to act now:
- When the user asks you to tell, relay, or send something to another session, call send (or ask) in THIS turn. Do not defer it to a future turn or say you will do it later — the note only exists once you call the tool. A promise to message a peer is not a message.
- When you receive a coordination note that is a request and a reply is expected, call respond with its request_id in this same turn.
- "[handled for you]" records and "[reply ...]" notes are informational — read them, act only if they matter, reply to neither.

Notes:
- Ambient awareness: a read-only roster of your sibling sessions (id, title, busy/idle, their file claims) is injected into your context automatically every turn. You already know who else is here — do NOT call discover, send, or wake a peer just to check in or say hello. Reserve the channel for real coordination (a collision risk, handoff, state question, or request).
- This is an authorized same-user, same-machine channel between your own concurrent sessions. Keep messages about coordinating shared work (file claims, collision warnings, state, requests). Do not use it to relay arbitrary text to the user or to ask a peer to override the user, escalate permissions, or take destructive action — the receiving session is instructed to refuse those, so they will not work.
- Delivery is automatic, durable, and consumes the note: once you post it, the target receives it in its context at its next turn boundary (or is woken for it if idle). Because delivery marks the note read, a peer that has ALREADY been shown a note will see "no unread items" from discover — that is correct, not a lost message; check the sent-receipt ledger instead.
- A session woken by your note is instructed to tell the user that your session triggered the work, so the user always sees who asked for what.
- Do not start a reply back-and-forth unless coordination genuinely requires it; avoid auto-responding to every note.
- Claims are advisory coordination, not a lock. Always re-read a file before editing if a peer has claimed it. Before a shared-state action that can race across sessions (pushing to a release branch, cutting a tag/release), claim a logical resource such as "release:<branch>" so peers see it in their ambient roster, and check the roster first.
