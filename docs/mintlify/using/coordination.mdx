---
title: "Cross-session coordination"
description: "Run several PrioriCode sessions on one project and let them query each other, ack each other, and announce repo-wide moves via the sessions tool."
---

You can run five agents on one repo. Whether they finish the feature or merge into a knife-fight depends on whether they know about each other. PrioriCode gives them that: a durable, cross-process coordination channel built into the product.

## The setup

Start multiple `prioricode` processes in the same project (two terminals, tmux panes, whatever). They share state through the project's local database — session presence and messages live in a `session_coordination` ledger backed by SQLite (WAL mode), so coordination works across processes and survives a crash.

Every session automatically knows who its siblings are: a read-only roster (id, title, busy/idle) is injected into each agent's context on every turn — no polling. And whenever a **new session** receives its first user message, it announces itself to every live peer: session id, title, and a gist of its first task. Peers learn about new arrivals without anyone asking. In the TUI, `/coordination` opens the ledger; a footer indicator marks unread notes and escalations.

## The three actions

From inside a session, the agent uses the `sessions` tool — and it has exactly three verbs:

| Action      | Kind        | What it does                                                                                                                                                                                                                                                                                                                            |
| ----------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `query`     | ask or tell | A durable note into one peer's inbox, with or without a question in it. Fire-and-forget: a busy peer reads it at its next step boundary, an idle peer wakes within seconds. The answer arrives back in the asker's own context later — nothing blocks.                                                                                  |
| `respond`   | reply + ACK | The universal answer primitive, keyed by `request_id`. **Every note a session receives owes exactly one respond** — a real answer or a one-line ack. Exactly one respond per note, enforced at the database level. Corrections ride a new `query`.                                                                                      |
| `broadcast` | announce    | Fires a `query` to every live peer at once (sharing one group id) before a big shared-state move — `git stash`, `git reset`, branch switches, pushes to shared branches. It does not wait and there is no approval gate: peers whose work is affected query the broadcaster with an objection, and objections are handled as they land. |

The tool contract itself — the guidance the agents follow — lives in the product at `cli/src/tool/sessions.txt`. It reads like good office etiquette: don't wake anyone to say hi, don't re-query after a timeout, never respond to a reply.

Negotiations thread: a `query` can carry a prior `thread_id` to continue an exchange with full context instead of starting fresh.

## Knowing who changed what

Guessing whose edit landed in the working tree is how multi-agent work turns into a knife-fight — "not mine, so I won't ship it" fractures commits, or worse, one agent absorbs another's half-finished work. PrioriCode answers the question with a durable **file-touch ledger** instead of vibes:

- **Every tool write is fingerprinted.** `edit`, `write`, and `apply_patch` record one row per file — which session, which operation (create/modify/delete), which model, the timestamp, and pointers to the message and tool call whose stored diff shows exactly what changed. One row per path, last writer wins.
- **Out-of-band edits are recorded too.** The file watcher stamps changes that arrive through no PrioriCode tool (your editor, a shell command) as `external`, deduped by fingerprint so a session's own recorded write is never misattributed. Absence of any row means: nobody in this system wrote it — ask the user.
- **Agents can query it.** `sessions` with `query` + `paths` is a local ledger read (no peer involved): for each path the answer is _you_, _a named peer with a hunk excerpt_, _outside PrioriCode tools_, or _no record_. The contract tells agents to run this before touching or shipping foreign paths — never silently narrow a commit to "only mine" and never commit a peer's work-in-progress without asking them.
- **Edits warn on the spot.** When a file changed since an agent last read it, the next edit's result names the last recorded writer and tells it to query that peer before overwriting.
- **Commits stay blameable.** The advisory reminds a committing agent to add a `PrioriCode-Session: <id>` trailer, so `git blame` resolves committed lines back to the session that wrote them.
- **`git status` gets annotated.** When a session runs `git status`, `add`, `commit`, `push`, or `stash` while peers are active, the shell output marks dirty paths that are not its own, with their owners — advisory, never blocking.

Disable the ledger entirely with `PRIORICODE_DISABLE_FILE_TOUCH=1`. The recommended discipline while per-session worktrees become standard: give each agent its own `git worktree` (`git worktree add ../wt-x -b x`), let them merge through git, and let the ledger + `/coordination` keep the humans out of the loop's way.

## Properties the channel keeps

- **Everything is traceable.** Every row carries sender, recipient, the assistant message (and tool call) that produced it, its group for fan-outs, and the full lifecycle: created → injected into the peer's context (stamped with the receiver's turn id) → acknowledged → responded. The `/coordination` ledger shows the state per note with timestamps; sessions also see an ambient "outstanding notes" count.
- **Nothing is silently dropped.** Delivery is exactly-once at turn boundaries; a crashed delivery is re-queued and re-delivered.
- **Silence escalates — once.** A query nobody answers past the deadline is **escalated to you** (the human), then expires (terminal) after a further grace. Broadcasts and announces never escalate; only direct queries do.
- **Only queries and replies wake.** Ambient rows (announcements, ledger records) never burn a model turn — the loop-breaker that keeps chatty sessions from infinite-looping each other. Reply chains also terminate by structure: you cannot respond to a response.
- **Presence is cross-process truth.** Each process mirrors busy/idle transitions into a presence table with heartbeats; a crashed session reads as idle after its heartbeat goes stale (72 h marks roster entries stale and skips them as announce targets).
- **A watcher does the boring waiting.** A lightweight watcher (2-second cycle) wakes idle peers with unread queries, recovers crashed deliveries, escalates and expires overdue notes, and posts the session-init announces — no polling loops anywhere.

<Note>
  Rate limits keep things sane: 10 notes/minute per sender-recipient pair (tune
  `PRIORICODE_COORDINATION_RATE_LIMIT_PER_MINUTE`), 5-minute dedupe window for identical repeats while the original is
  unprocessed, inbox cap of 50, and a 15-minute escalation deadline (`PRIORICODE_COORDINATION_ESCALATION_MS`).
</Note>

## Using it as a human

You benefit from coordination even if you never touch the tool:

- **Split the work.** "You two: one does the migration, one does the UI" — each session can simply `query` its sibling about what it's touching and negotiate, and edit-time collision notices nudge agents to re-read before overwriting.
- **Stay in charge of escalation.** If a peer can't answer, the query surfaces to you; `/coordination` counts them and the footer shows a warning.
- **Audit.** `/coordination` shows every note you received and sent with its lifecycle state (`pending`, `injected`, `acked`, `answered`, `escalated`, `expired`), group attribution for broadcasts, and ages.

## Try it for real

The quickest way to trust it:

```bash
# terminal A
cd your-project && prioricode
# terminal B
cd your-project && prioricode
```

In A: _"Ask your sibling session what it's working on and report back."_ A's agent `query`s B; B's footer lights up; the reply lands in A's context and the agent reports it. Now start a third session C and give it a task — A and B each receive C's announce within seconds, and owe it one short ack.

<Note>
  Coordination is permission-gated per action — like everything else in [permissions](/using/permissions), the agent
  asks before it messages. Older saved rules keyed to the removed actions (`send`, `ask`, `wait`, `notify`, `claim`,
  `release`) no longer match anything; re-grant them for `query`/`respond`/`broadcast` if you had per-action rules.
</Note>
